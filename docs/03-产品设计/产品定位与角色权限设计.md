# 产品定位与角色权限设计

> **本文件是产品的「地基文档」。** 它回答三个问题：① 这个产品为什么存在、给谁用、在哪用（定位与范围）；② 谁在什么条件下能做什么（角色与权限）；③ 我们用什么流程把它做对（研发流程）。
>
> 背景：项目此前是「先做功能，再补设计」——点评、认领、签到都做出来了，但**没有先定义「谁能做什么」**，于是暴露出「学生能顶替别人身份」「学生自己说答对了就加分」「切到别的班没人拦」等问题。本文档是 Phase 3 的**设计基线**，此后所有功能设计必须与本文对齐。

---

## 一、产品目的（Why）

### 1.1 一句话

> 把小学科学课堂里**看不见的正向行为**，变成**看得见的成长**。

### 1.2 三层目的与成功标志

| 层 | 目的 | 成功标志（可观测） |
|---|---|---|
| **学生** | 愿意参与科学课堂，愿意观察、提问、表达 | 课后/课间**主动**打开学生端与伙伴互动 |
| **老师** | 让「维持课堂正向行为」变成零负担 | 每节课都打开；点评 2 步完成；不打断教学 |
| **班级** | 形成「一起把星球养大」的合作氛围 | 生态值持续增长；关系藤蔓网越来越密 |

### 1.3 反向定义：我们**不做**什么

- ❌ 不做通用积分榜 / 排名工具（不做「谁第一谁最后」的羞辱）
- ❌ 不做作业批改、成绩管理、考试系统
- ❌ 不做家校沟通 / 家长端（当前阶段）
- ❌ 不做需要安装的 App / 小程序 / 客户端
- ❌ 不采集隐私（无手机号、无头像上传、无定位）

> 目的不清 → 功能会失控。之前的「学生能自己加分」正是**目的漂移**：把「激励工具」做成了「谁都能改分的系统」。定位先锁死，再做功能。

## 二、使用范围（Who / Where / When）

### 2.1 用户 · 设备 · 场景

| 角色 | 设备 | 场景 | 频率 |
|---|---|---|---|
| **老师（李钰琳）** | 教室电脑 + 投影大屏 | 上课过程中点评、看全班大屏 | 每节课 |
| **老师（李钰琳）** | 办公电脑 / 家里 | 建班、导入名单、调伙伴、看数据 | 每周 |
| **学生（1–6 年级）** | 自己的平板 / 手机 / 机房电脑 | 课前签到、课间互动、课后延续 | 每天 |

### 2.2 时间轴（一节课的完整周期）

```
【课前 Before】 老师登录 → 选「当前班级」→ 授权（进入授课会话）
                学生进班 → 选自己 → 与伙伴打招呼

【课中 During】 老师点评（两步点击）→ 伙伴即时反馈 → 大屏氛围
                ★ 老师专属操作窗口：加分 / 撤销 / 改信息 / 删人

【课间与课后 After】老师下课 → 关闭会话（收回权限）
                学生互动：签到 / 答题 / 观察 / 作业 —— 只能「正确操作才加分」
```

### 2.3 范围边界（当前不做，与 [`项目简介 §5`](../01-项目概览/项目简介.md) 一致）

不做 App / 小程序；不引前端框架；不做通用积分；不采集隐私；不做排名羞辱。

## 三、角色与权限模型（Who can do What）

### 3.1 三个角色

| 角色 | 系统身份 | 说明 |
|---|---|---|
| **老师** | `teachers` 表 + JWT 登录（已有） | 一个老师管自己的班，互不可见 |
| **学生** | 无账号，凭班级码 + 学生条目 + **设备令牌** | 只能做「合格互动」，不能改分改信息 |
| **运营 / 研发** | 服务器 SSH | 部署、迁移、救援，不直接碰生产学生数据 |

### 3.2 权限矩阵（目标态）

| 操作 | 老师 | 学生 | 前置条件 |
|---|:---:|:---:|---|
| 建班 / 删班 / 改班 | ✅ | ❌ | 老师登录 |
| 导入 / 改名 / 删学生 | ✅ | ❌ | **老师登录 + 该班授课会话** |
| 修改伙伴角色 / 昵称 / 颜色 | ✅ | 🟡 仅认领/重新认领时 | 学生只能改「自己的」伙伴 |
| 课堂点评加分 / 撤销 | ✅ | ❌ | **授课会话内** |
| 查看全班状态 / 明细 | ✅ | ❌ 仅自己 | — |
| 切换班级 | ✅ | ❌ | **需要切班密码** |
| 每日签到 / 答题 / 观察 / 作业 | ❌ | ✅ | 免登录；**服务端按动作定分** |
| 给自己加分（任意值） | — | ❌ | 分值永远由服务端决定，前端不可传分 |

> 图例：✅ 允许 ｜ ❌ 禁止 ｜ 🟡 受限允许

### 3.3 权限的「授予 — 收回」：授课会话（Lesson Session）

这是本设计的核心机制，直接回答「课前怎么授予老师权限、下课怎么收回」。

```
① 老师登录（账号 + 密码）
        ↓
② 选择「当前班级」＋ 开始上课（点「开始上课」按钮）
        ↓  后端签发「授课会话令牌」(lesson token, 有效期如 90 分钟，绑定 teacher_id + class_id)
③ 课中：所有「老师专属操作」都携带 lesson token → 后端校验 → 放行
        ↓
④ 下课（点「下课」，或令牌自然过期）
        ↓  前端清除令牌；后端令牌失效
⑤ 会话外：老师仍可看班级列表与历史数据，但**无法再改分/删人**
```

**为什么用「会话」而不是「登录态」？**
登录态是长期的（30 天 JWT），上课是**短时的**。用短时令牌把「高危操作」的窗口压缩到一节课，即使老师的电脑被学生碰到、或手机被人借走，下课后也无法改分。

### 3.4 学生权限收敛（本设计的第二个核心）

学生端**永远不做**以下几件事：

1. **不能自主加分**——分值只由服务端按「动作类型」决定（`kind` → points）。
2. **不能改别人的信息**——只能操作自己的学生条目（凭设备令牌绑定）。
3. **不能切换/浏览其他班级**——切班需要密码（老师专属）。
4. **不能自证正确**——答题对不对，由**服务端判分**，不是学生点「我答对了」。

一句话：**学生只能「做对」才得分，不能「说自己对」就得分。**

## 四、班级访问与切换保护

### 4.1 老师独立登录 · 各带各班

- 每个老师用自己的账号登录（`teachers` 表已有 `teacher_id`，`assertOwnsClass` 已做数据隔离）。
- 老师只能看到 / 操作自己名下的班级与学生。**多老师天然隔离**，无需额外开发，只需把「老师注册 / 账号分配」补齐。

### 4.2 上课选班

- 老师登录后看到自己的班级列表（卡片墙）。
- 点「开始上课」→ 选中「当前班级」→ 进入该班的授课会话。
- 大屏顶部常驻显示当前班级名，避免老师上错班。

### 4.3 切换班级需要密码（防学生课间串班）

**问题场景**：老师在教室电脑上打开 A 班大屏，下课后学生围过来乱点，切到 B 班，甚至改了 B 班的数据。

**解法（两道锁）**：

| 锁 | 机制 | 效果 |
|---|---|---|
| 第一道：授课会话 | 切班 = 结束当前会话，必须重新验证 | 学生没有密码，切不过去 |
| 第二道：切班密码 | 切换班级时要求输入「老师密码」或「切班 PIN」 | 即使会话还在，切班也要再输一次 |

> **建议**：切班密码直接用老师登录密码（不额外记一个），或老师可在设置里设一个 4 位「课堂 PIN」。

## 五、学生身份识别与「认领」修正

### 5.1 现状问题（本轮用户反馈）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 打开入班链接，**直接跳到某个已认领的同学** | 学生端 `init()` 读 `localStorage.gp_me`，只要有记录就 `restoreHome()` **跳过「选自己」**；且用的是**上次保存的班级码**，甚至可能跨班 |
| 2 | 「切换账号 / 重新认领」点了之后，**改不了伙伴** | `resetAll()` 只清 localStorage 回到第一步；重选名字时因 `partner_kind` 已存在，`pickStudent()` 直接 `loadHome()`，**没有进入「选伙伴」步骤** |
| 3 | 谁都能点别人名字进主页 | 认领后无任何归属校验，`claim` 接口免登录、无令牌 |

### 5.2 修正原则

1. **链接只带班级码，不带身份**——`?code=XXXX` 永远只用于「进班」，不用于「我是谁」。
2. **每次打开，先「选自己」**——不再自动恢复上次身份；已认领的信息在选中自己名字后才展示。
3. **认领后签发「设备令牌」**——认领成功时，服务端给该学生生成一个 `device_token`，存本机；之后写活动凭令牌校验，防止顶替。
4. **提供明确的「重新认领 / 换伙伴」入口**——允许学生改伙伴（这也符合「养成 + 收集」的心理动机），但会记一次 `partner_claims` 变更历史。
5. **跨班不串**——令牌绑定 `class_id`，A 班的令牌在 B 班无效。

> 这部分对应需求 R45 / R46 / R52，落地前需先定「设备令牌」的存储与校验方式（见第八节 Open Questions）。

## 六、「课间答题 / 互动加分」重构（重点）

### 6.1 现状（错在哪）

当前实现（`partner-demo.html` 的 `doActivity`）：

```js
if(kind==='quiz'){
  const ok = confirm('你答对这道题了吗？\n确定=答对(+2)，取消=答错');
  body.correct = ok;      // ← 错在这里：由学生自己声明对错
}
```

**问题**：
1. **没有题目**——工具不出题，学生面对的是一个「你答对了吗」的自证弹窗。
2. **判分由学生说了算**——学生点「确定」就 +2，等于**自助加分**，与「学生不能随意加分」的定位直接冲突。
3. **无法沉淀知识**——没有题干/知识点字段，答题历史只有「对/错」，不产生教学价值。

### 6.2 目标逻辑（正确形态）

```
① 学生点「课间答题」
        ↓
② 前端向服务端要一道题：GET /api/quiz/next?student_id=...（服务端按年级/单元抽题，不含答案）
        ↓
③ 学生点选 A / B / C / D
        ↓
④ 提交作答：POST /api/students/:id/quiz  { question_id, choice }
        ↓
⑤ 服务端比对答案 → 判对错 → 定分（对 +2，错 0）→ 返回正误 + 解析
        ↓
⑥ 前端反馈：答对→伙伴跳动 +2；答错→展示解析，不加分，可再来一题
```

**关键点**：答案只在服务端，`choice` 由学生点选，**判分权在服务端**。前端拿不到答案，也就无法作弊。

### 6.3 五类互动的加分规则（服务端定分，前端不可传分）

| 互动 | kind | 学生做什么 | 加分条件 | 分值 | 限频 |
|---|---|---|---|---|---|
| 每日签到 | `checkin` | 点「签到」 | 每天一次 | **+1** | 1 次/天 |
| 课间答题 | `quiz` | **选答一道题** | 服务端判**答对** | **+2**（错 0） | 建议 3 题/天 |
| 观察记录 | `observe` | 写一条观察 | 内容非空且 ≥8 字 | **+1** | 建议 2 条/天 |
| 提交作业 | `homework` | 写一句完成了什么 | 由老师课后确认（见下） | **+3** | 1 次/天 |
| 老师点评 | `event` | — | 老师点标签 | 按标签 +1~+3 | 老师操作 |

> **优化建议**：`homework`（+3）目前是「学生写一句就 +3」，也属于「自证得分」。建议改为**老师课后确认制**：学生提交 → 进入「待确认」→ 老师在大屏点「确认完成」才 +3。这样作业分才真实。（对应 R52 的延伸）

### 6.4 防刷分（服务端硬约束）

- 分值映射写在服务端常量，**请求体不接受 `points` 字段**（已有）。
- 判分逻辑在服务端，**请求体不接受学生自报的 `correct`**（本次要改）。
- 关键互动加**每日次数上限**（签到已限；答题/观察/作业建议加）。
- 认领 + 活动写操作**校验设备令牌**，杜绝「替别人加分」。

### 6.5 落地分期

| 阶段 | 内容 | 依赖 |
|---|---|---|
| Phase 4-A | 去掉自证弹窗；`quiz` 改为「服务端出题 → 判分」（**先小步**：题库可先用老师手填的少量题） | R47 + R33 |
| Phase 4-B | 建 `questions` 表 + 老师端录入界面 | R33 |
| Phase 4-C | 作业改为老师确认制；观察加限频 | R52 延伸 |

## 七、研发流程（How we build）

### 7.1 我们现在的思路对在哪、错在哪

- **对的**：小步提交、每步验证、文档留痕（`docs/` 已成型）。
- **错的**：**从「功能」出发，而不是从「定位」出发**。
  - 先做了「认领」「签到」「答题」这些功能，却没有先定义「谁是学生、学生能做什么」——于是出现身份可顶替、可自助加分。
  - 先做了「多班」数据，却没有先定义「老师怎么授权、怎么收回」——于是出现课间串班风险。

**结论：不是流程「不规范」，而是缺了最前面的两块地基——「定位」与「角色权限」。补上它们，后面的功能才不会反复返工。**

### 7.2 标准流程（六阶段，从定位开始）

```
① 定位        产品目的 · 使用范围 · 成功标准            ← 本文档 §一、§二
② 角色权限    谁 · 何时 · 能做什么（权限矩阵 + 会话）    ← 本文档 §三、§四
③ 需求        用户故事 + 验收标准（可测试）              → 需求清单
④ 交互设计    页面 · 步骤 · 状态 · 空态/异常态           → 产品设计
⑤ 技术设计    数据模型 · 接口 · 时序 · 安全              → 技术设计
⑥ 实现 → 验收 → 复盘 → 运营迭代                          → 提交 / 验收清单 / 故障复盘
```

**每个阶段都有「产出物 + 验收门」**：上一阶段的产出物不通过，不进入下一阶段。

### 7.3 本项目的产出物映射

| 阶段 | 产出物 | 存放位置 |
|---|---|---|
