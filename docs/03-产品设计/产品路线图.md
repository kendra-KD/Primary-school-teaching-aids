> 目标：把「工具」变成「教学环节的一部分」。回答用户提出的「结合上课内容加分升级」与「课间总结知识点问答」。

| 编号 | 功能 | 优先级 | 交付物 |
|---|---|---|---|
| R33 | **科学知识点题库** | P1 | `questions` 表（年级/单元/题干/选项/答案/解析）+ 抽题接口 + 老师端录题页；学生端从题库抽题，服务端判分 |
| R34 | **老师端互动明细** | P1 | `GET /api/classes/:id/activities`；点学生卡片弹侧栏，看该生「签到/答题/观察/作业」记录 |
| R32 | **学生端提交作业入口** | P2 | 复用 `homework` 分支（+3），按钮已定义仅需渲染 |
| R30 收口 | **标签 ↔ 课时知识点映射** | P1 | 建课时可选「本课推荐标签」，dock 只显示相关标签，减少老师选择成本 |
| R20 收口 | **视觉打磨** | P2 | 卡片密度与留白优化；1366×768 小屏适配验证 |

**Phase 4 出口标准**：老师能在课堂上完成「讲新课 → 学生答题 → 结果进大屏」的完整闭环。

## 五、明确不做（Won't Do）

| 事项 | 理由 |
|---|---|
| 家长端 App | 超出「课堂即时反馈」定位；隐私风险高 |
| 成绩管理 / 考试分析 | 与教务系统重叠，不是科学课特有需求 |
| 通用积分（跨学科） | 会稀释「科学学科专属」的差异化 |
| 学生端账号体系 | 与「小学生零门槛」原则冲突 |
| 排行榜公开排名（含负向） | 与「不羞辱」原则冲突 |
| 引入前端框架重写 | 单文件 HTML 的「双击即用」是不可替代的优势 |

## 六、优先级判定原则

1. **老师上课会用到吗？** 不会用的功能一律排后。
2. **会不会增加老师工作量？** 会增加的（如必须提前录题）必须提供「零备课默认值」。
3. **有没有羞辱学生的风险？** 有风险的一律重新设计或不做。
4. **是否服务于「科学学科」定位？** 通用能力优先级低于学科能力。
5. **能不能单点交付？** 不能拆成一次可验收的小步的，先拆小。
