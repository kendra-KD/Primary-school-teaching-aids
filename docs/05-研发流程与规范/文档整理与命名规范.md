# 文档整理与命名规范

## 1. 目标

1. **一处找得到**：任何人（老师、新研发、审计）都能在 30 秒内定位到想要的文档。
2. **不重复**：同一个事实只在一个文件里定义，其它地方引用链接。
3. **不过期**：文档与代码在同一提交内同步；线上行为以文档描述为准。
4. **可溯源**：需求 → 设计 → 代码 → 验收 → 发布，全链路可追。

---

## 2. 目录结构规范

```
docs/
├── README.md                     # 唯一入口：文档地图 + 角色阅读路径 + 维护约定
├── 01-项目概览/                   # 「是什么、给谁、到哪了」——新人和外部人员第一站
├── 02-需求/                       # 需求全生命周期（PRD / 台账 / 追溯矩阵）
├── 03-产品设计/                   # 路线图、画像、图鉴、交互设计
├── 04-技术设计/                   # 架构、数据库、接口、ADR
├── 05-研发流程与规范/             # 流程、代码规范、文档规范
├── 06-测试与验收/                 # 验收清单、故障复盘
├── 07-部署与运维/                 # 部署、监控、排障
├── 08-项目历程/                   # 开发日志、CHANGELOG、需求来源原始记录
└── 90-历史设计资料/               # 归档：早期调研与设计稿，仅溯源用
```

**编号规则**

| 区段 | 含义 |
|---|---|
| `01`–`08` | **活跃文档**，随项目演进持续更新 |
| `90`–`99` | **归档区**，只读不改；新内容不得放这里 |
| 未来扩展 | 依次使用 `09`、`10`…，不要插空位（避免字母序错乱） |

**为什么用数字前缀**：保证文件管理器与 Git 列表里顺序稳定且符合阅读逻辑，不依赖手动排序。

---

## 3. 文件命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 目录 | `NN-中文短语`，无空格 | `04-技术设计` |
| 说明文档 | 中文短语，必要时括号补限定 | `系统架构设计.md`、`伙伴图鉴设计（38种）.md` |
| 编号类文档 | `类型-名称.md` | `PRD-产品需求文档.md`、`ADR-架构决策记录.md` |
| 归档文件 | 保留原英文名 + 不改动内容 | `requirements-research.md` |
| 原始稿 | 名称后加「（原始稿）」 | `后端架构与部署方案（原始稿）.md` |

**禁止**：空格、`final`、`new`、`v2`、`副本`、`临时`、纯日期文件名（日期放正文里）。
> 「final-design-report.md」正是反面教材——所以它被归档到了 `90-历史设计资料/`。

## 4. 文档内容规范

### 4.1 每篇文档必须有的头

```markdown
# 文档标题

> 一句话说明本文档解决什么问题、面向谁。

（正文）
```

关键文档（PRD、需求台账、接口文档、数据库设计）额外加**元信息表**：

```markdown
| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 最后更新 | 2026-09-11 |
| 维护人 | 研发 |
| 关联文档 | [链接] |
```

### 4.2 写法约定

| 规则 | 说明 |
|---|---|
| **先结论后论证** | 表格与清单优先于长段落 |
| **状态要有标记** | ✅ 已实现 ｜ 🟡 部分实现 ｜ 🔴 未实现 ｜ ⚫ 已废弃 |
| **不写「应该/大概」** | 写实际值、实际路径、实际行号；不确定就标注「待确认」并记入待办 |
| **代码位置要精确** | 写 `server/src/routes/events.js:155`，不写「改一下那个查询」 |
| **禁止空话** | 不写「本系统设计精良、性能优异」，写「接口 P95 < 300ms」 |
| **历史不改写** | 归档文档保持原样；需要更新则另起新文档并说明取代关系 |

### 4.3 图表

- 结构/流程用 **ASCII 图**（Git 友好、无依赖、任何编辑器都对齐）；
- 关系用**文字表格**描述，不强制画 ER 图；
- **禁止**在文档里嵌入图片二进制（`90-历史设计资料/` 里的原有图片引用除外）。

## 5. 文档与代码的同步责任

| 代码变更 | 必须同步更新的文档 |
|---|---|
| 新增/修改接口 | `04-技术设计/API接口文档.md` |
| 表结构变更 | `04-技术设计/数据库设计.md` + `deploy/*.sql` |
| 新增/修改伙伴种类 | `03-产品设计/伙伴图鉴设计（38种）.md` + 两个前端文件 |
| 标签分值/新增标签 | `01-项目概览/项目简介.md`（标签表）+ `03-产品设计/课堂点评与学生互动闭环设计.md` |
| 需求状态变化 | `02-需求/需求清单与实现状态.md` + `需求追溯矩阵.md` |
| 任何上线变更 | `08-项目历程/CHANGELOG.md` |
| 架构取舍 | `04-技术设计/架构决策记录ADR.md`（新增 ADR-##） |
| 线上故障 | `06-测试与验收/故障复盘记录.md` |
| 部署方式/命令变化 | `07-部署与运维/部署手册.md` |

> **原则**：文档更新与代码改动**同一个提交**完成。不允许「先上线，文档回头补」——除非在 `08-项目历程/开发日志` 里显式记一条待补。

## 6. 归档规则

满足以下任一条，文档移入 `90-历史设计资料/`：

1. 描述的是**已被取代**的方案（如 `final-design-report.md` 被规范 PRD 取代）；
2. 前置调研材料，其结论已吸收进正式文档（如 `requirements-research.md`、`teacher-interview-outline.md`）；
3. 一次性活动材料（如 `小红书-想法征集文案.md`）。

**归档操作**：
- 用 `git mv`（保留历史），不要删除重建；
- 不改内容（保持可溯源），在 `docs/README.md` 的目录地图中说明其定位；
- 若结论仍有效，在正式文档中以链接引用它。

## 7. 文档质量检查清单

写完/改完一篇文档，过一遍：

- [ ] 头部有标题 + 一句话说明
- [ ] 关键文档有元信息表（版本/日期/维护人/关联）
- [ ] 所有状态都有标记（✅/🟡/🔴/⚫）
- [ ] 所有代码引用都到「文件:行号」级别
- [ ] 没有「应该」「大概」「可能」这类模糊表述
- [ ] 没有本可删除的空话与自我表扬
- [ ] 相关文档的链接可达（相对路径正确）
- [ ] 索引（`docs/README.md`）中的地图已被更新
- [ ] 未把历史结论写成现状（必要时注明时间点）
