# 研发流程规范

> 本文档定义本项目的**标准开发流程**，参考了 Kubernetes（KEP）、Rust RFC、GitHub Flow、以及 Google 工程实践中的通行做法，并按「单人 + 小步快跑 + 课堂工具」的实际情况做了裁剪。

---

## 1. 总流程（六阶段）

```
① 需求登记  →  ② 方案设计  →  ③ 实现  →  ④ 自检验证  →  ⑤ 发布部署  →  ⑥ 复盘沉淀
   R## 编号      必要时写 ADR     小步提交     构建/冒烟/验收      tag + 上线      日志/复盘/文档
```

**每个阶段都有「出口条件」，不满足不进下一阶段。**

| 阶段 | 输入 | 动作 | 输出 | 出口条件 |
|---|---|---|---|---|
| ① 需求登记 | 老师反馈 / 用户原话 / 巡检发现 | 在 `02-需求/需求清单与实现状态.md` 登记 `R##`，判定优先级 | 一条带编号的需求 | 有编号、有优先级、有验收标准 |
| ② 方案设计 | 需求编号 | 判断是否影响架构；影响则写 `ADR-##` | 设计说明（可口头，但涉及取舍必须落文档） | 能说清「做什么/不做什么/代价是什么」 |
| ③ 实现 | 设计说明 | 只改必要文件；单次提交只做一件事 | 代码 | 本地跑通（双击可用 / `npm run dev` 无报错） |
| ④ 自检验证 | 代码 | 走「自检清单」+ 关键路径冒烟 | 验证记录 | 见 §3 自检清单，全部通过 |
| ⑤ 发布部署 | 通过验证的提交 | 打 tag → 推 GitHub → 服务器拉取构建部署 → 线上验证 | 线上可用版本 | 线上关键路径 200 + 人工点通 |
| ⑥ 复盘沉淀 | 发布结果 | 更新 CHANGELOG / 需求状态 / 追溯矩阵；故障另写复盘 | 文档同步 | 文档与线上一致 |

## 2. 分支与提交策略

### 2.1 分支模型：**GitHub Flow（trunk-based 简化版）**

```
main ──────●────────●────────●──────▶  始终可部署
            \      /  \      /
             ●────●    ●────●            功能分支（可选）
```

- `main` 始终保持**可部署状态**；
- 单人开发、功能小、迭代快 → **允许直接提交 `main`**，但必须：
  1. 单次提交只做一件事（可追溯到单个 `R##`）；
  2. 提交前必须走完 §3 自检清单；
- 以下情况**必须开分支**：改数据库结构、改部署配置、重构超过 200 行、并行做两件以上互不相关的事。

### 2.2 提交信息规范（Conventional Commits 的中文变体）

```
[类型] 一句话说清「做了什么」；必要时用分号追加第二件事

可选正文：
- 为什么这么改（根因 / 背景）
- 影响范围
```

| 类型 | 用途 | 例子 |
|---|---|---|
| `[feat]` | 新功能 | `[feat] 学生与伙伴互动闭环：签到/答题/观察 + 生态值成长` |
| `[fix]` | 缺陷修复 | `[fix] 鉴权钩子缺失 return 导致鉴权失败回退成 500` |
| `[ui]` | 界面/体验调整 | `[ui] 建班年级文案简化、密码眼睛、dock 收起` |
| `[docs]` | 文档 | `[docs] 建立 docs/ 文档中心` |
| `[refactor]` | 重构（不改行为） | `[refactor] 抽出 studentActivityView` |
| `[chore]` | 构建/配置/杂务 | `[chore] 升级 fastify 到 5.2` |

**要求**：
- **一句话能读懂改了什么**，不写「修复 bug」「优化代码」这类无信息量的描述；
- `[fix]` 必须说明**根因**（例：`鉴权钩子缺失 return 导致…`，而不是 `修复登录报错`）；
- 一次提交不要混入不相关改动。

## 3. 开发自检清单（提交前必须逐条过）

### 3.1 代码层

- [ ] 代码能无错误运行（前端：浏览器控制台无报错；后端：`node src/index.js` 无异常退出）
- [ ] 所有 import/依赖已添加，`package.json` 已同步
- [ ] 命名清晰无拼写错误
- [ ] **无硬编码密钥/密码**（一律走环境变量）
- [ ] 边界条件已处理（空数组、null、超长字符串、非法 UUID）
- [ ] 所有 SQL 使用参数绑定（`$1,$2...`），**无字符串拼接**
- [ ] 前端所有用户输入展示都经 `esc()` 转义（防 XSS）
- [ ] 新增/修改的 SQL 若含 `GROUP BY`，**SELECT 中的非聚合列必须出现在 GROUP BY 里**（历史事故见 `06-测试与验收/故障复盘记录.md`）

### 3.2 功能层

- [ ] 正常路径走通
- [ ] 异常路径有友好提示（不是 500、不是空白页、不是英文堆栈）
- [ ] 弱网/接口失败时界面不崩（前端降级到本地数据）
- [ ] 权限：非本人数据不可访问
- [ ] 手机上打开不破版（学生端主要入口）

### 3.3 数据层

- [ ] 表结构有变更 → 已写**幂等**迁移脚本，且 `init.sql` 已同步更新
- [ ] 迁移脚本可重复执行（用 `IF NOT EXISTS` / `DROP CONSTRAINT IF EXISTS`）
- [ ] 无破坏性操作（`DROP TABLE` / `UPDATE` 无 `WHERE`）

### 3.4 文档层

- [ ] 接口有变更 → 更新 `04-技术设计/API接口文档.md`
- [ ] 表结构有变更 → 更新 `04-技术设计/数据库设计.md`
- [ ] 需求状态有变更 → 更新 `02-需求/需求清单与实现状态.md` 与 `需求追溯矩阵.md`
- [ ] 本次改动已写入 `08-项目历程/CHANGELOG.md`

## 4. 验证策略（当前与目标）

### 4.1 现状（Phase 2.1）

| 层级 | 手段 | 覆盖 |
|---|---|---|
| 语法/构建 | 手工：打开页面看控制台；后端看启动日志 | 100% |
| 接口 | `curl` 冒烟（登录 → 拉班级 → 拉状态） | 关键接口 |
| 功能 | 人工逐条走验收清单 | 关键路径 |
| 回归 | 人工 | 依赖经验 |
| 线上 | 日志 + Umami + 人工点通 | 全部部署 |

**诚实说明：本项目目前没有自动化测试。** 单一开发者 + 快速迭代 + 极小代码量（后端约 500 行）时，人工验证的性价比更高。但这个债必须还。

### 4.2 目标（Phase 4 起）

| 优先级 | 事项 | 说明 |
|---|---|---|
| P1 | 后端最小集成测试 | 用 `node --test` + 测试库覆盖：登录、班级 CRUD、`/state` 聚合（**正是出过 42803 的地方**）、点评与撤销 |
| P1 | 构建校验 | 部署前用 `node --check` 检查 `server/src/**/*.js` |
| P2 | 前端冒烟脚本 | 用 Playwright 或 `curl` 检查构建产物中 `GP_API_BASE` 已正确注入、无残留占位符 |
| P3 | GitHub Actions | push/PR 时跑「语法检查 + 测试」，失败即阻断 |

### 4.3 部署前必做的 3 条冒烟命令

```bash
# 1) 后端可用
curl -sS -o /dev/null -w '%{http_code}\n' https://gp.mealpick.me/api/health      # 期望 200

# 2) 登录链路（错误密码必须 401，不是 500）
curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://gp.mealpick.me/api/auth/login \
  -H 'Content-Type: application/json' -d '{"email":"luyulin@mealpick.me","password":"wrong"}'

# 3) 鉴权后核心接口（含 /state 聚合，易错点）
TOKEN=$(curl -sS -X POST https://gp.mealpick.me/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"luyulin@mealpick.me","password":"youPassword"}' \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).token))")
curl -sS -o /dev/null -w '%{http_code}\n' https://gp.mealpick.me/api/classes -H "Authorization: Bearer $TOKEN"
CID=$(curl -sS https://gp.mealpick.me/api/classes -H "Authorization: Bearer $TOKEN" \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const c=JSON.parse(s).classes[0];console.log(c?c.id:'')})")
[ -n "$CID" ] && curl -sS -o /dev/null -w '%{http_code}\n' \
  "https://gp.mealpick.me/api/classes/$CID/state" -H "Authorization: Bearer $TOKEN"   # 期望 200
```

## 5. 发布流程（Checklist）

```bash
# ── 本地 ──
cd e:\WorkBuddy\Tool\growth-planet-repo
git status && git diff                  # 确认改动范围符合预期
# 走完 §3 自检清单
git add -A && git commit -m "[fix] ..."
git push origin HEAD

# ── 服务器 ──
ssh root@39.102.215.224
cd /opt/growth-planet-new
git pull

# 只改前端：
bash deploy/build-frontend.sh
docker compose -f deploy/growth-planet-docker-compose.yml up -d

# 改了 server/ 或 Dockerfile：加 --build
bash deploy/build-frontend.sh
docker compose -f deploy/growth-planet-docker-compose.yml up -d --build

# 表结构有变更：先备份再迁移
docker exec gp-db pg_dump -U gp_app growth_planet > /tmp/backup_$(date +%F_%H%M).sql
docker exec -i gp-db psql -U gp_app -d growth_planet < deploy/growth-planet-migrate.sql

# ── 线上验证 ──
docker logs --tail 50 gp-api
curl -sS -o /dev/null -w '%{http_code}\n' https://gp.mealpick.me           # 200
# 执行 §4.3 三条冒烟命令
```

**发布后 5 分钟内必查**：
1. `docker logs --tail 50 gp-api` 无 `"level":50` 记录；
2. 老师端打开首屏 < 3s，无转圈；
3. 登录 → 建班/导入 → 点评 → 大屏刷新，全链路点通一次。

## 6. 故障响应流程（SOP）

```
发现异常
   │
   ├─ 影响上课？ ── 是 ──▶ ① 先回滚/降级（老师端可继续用本地模式）② 再排查
   │
   ▼
① 收集证据：docker logs --tail 80 gp-api（找 reqId + statusCode + err.stack）
            浏览器 Network / Console
② 定位根因：读错误信息 → 定位到具体文件与行（**先读错误，不要盲改代码**）
③ 一次性修复：找到原因后一次改好，不做「试试这个试试那个」的反复补丁
④ 重新验证：走 §4.3 冒烟 + 复现原路径
⑤ 48 小时内写复盘：现象 / 影响 / 根因 / 修复 / 预防 → 06-测试与验收/故障复盘记录.md
```

**三次原则**：同一个问题连续修 3 次仍未解决 → 停止盲改，向项目方说明「已尝试方案 + 当前判断 + 需要什么帮助」。

**红线**：
- ❌ 不分析原因就改代码
- ❌ 反复小修小补（修了 A 坏了 B）
- ❌ 隐瞒错误继续往下做
- ❌ 把大段调试日志甩给用户看
