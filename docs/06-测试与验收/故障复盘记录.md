## INC-001 页面 JS 全部泄露为文本，按钮全失效

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-07 |
| 提交 | `7ac1df7` |
| 严重度 | 高（页面完全不可用） |

**现象**：打开老师端，主区域空白，页面底部出现大段 JS 源码文本，所有按钮点击无反应。

**排查**：查看渲染后的 DOM，发现 `<script>` 提前闭合——JS 源码被当成 body 文本渲染。

**根因**：JS 注释中写了 `</script>`（在说明「在本文件 `<script>` 之前加一行」时直接写了该标签）。HTML 解析器在遇到注释里的 `</script>` 时**仍然会结束 script 元素**（HTML 的脚本数据状态不解析 JS 注释），导致后续代码全部落到 HTML 文本节点。

**修复**：把注释中的 `</script>` 改写为 `<\/script>`（转义斜杠）。

**验证**：页面正常渲染，所有按钮可用。

**预防**：
1. 在 HTML 内联 JS 中，**任何要显示 `</script>` 字样的地方必须写成 `<\/script>`**；
2. 已写入开发自检清单（[`../05-研发流程与规范/研发流程规范.md §3.1`](../05-研发流程与规范/研发流程规范.md)）；
3. 部署后必须打开页面看一眼（不能只看接口 200）。

## INC-002 登录按钮不显示

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-06 |
| 提交 | `fee26ac` |
| 严重度 | 高（无法登录） |

**现象**：部署后无痕窗口打开，右下角「☁ 登录同步」按钮不显示。

**根因**：`deploy/build-frontend.sh` 使用 sed **全局替换** `__GP_API_BASE__`。除了预期的赋值语句：

```js
window.GP_API_BASE = '__GP_API_BASE__';   // 想改成 ''
```

检查语句也被替换了：

```js
if (GP_API === '__GP_API_BASE__') GP_API = null;   // 被替换成 if (GP_API === '') GP_API = null;
```

结果 `GP_CLOUD` 计算错误 → 判断为「未配置云端」→ 登录入口不渲染。

**修复**：sed 表达式收窄为**只匹配赋值语句**：

```bash
sed "s/window\.GP_API_BASE *= *'__GP_API_BASE__'/window.GP_API_BASE = '${API_BASE}'/g" "$SRC/$f" > "$OUT/$f"
```

**验证**：构建产物中 `if(GP_API==='__GP_API_BASE__')` 保持原样，登录按钮显示且可登录。

**预防**：
1. 构建脚本中的替换必须**精确匹配**，禁止宽泛的全局替换；
2. 已在 `build-frontend.sh` 内写入注释说明「不要用全局替换」；
3. 部署验收清单加入 0.7「前端占位符已注入」检查项。

## INC-003 老师大屏长时间转圈打不开

| 提交 | `6e28c34` |

**预防**：
1. **任何第三方脚本一律延迟加载**，不得位于关键渲染路径；
2. 所有 `fetch` 必须带超时；
3. 长任务前必须有可见的 loading 态；
4. 已写入自检清单（前端第三条）。

## INC-004 删除学生 / 班级返回 500

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-10 |
| 提交 | `329dc66` + 迁移脚本第 4 节 |
| 严重度 | 中（可绕过，但影响老师维护花名册） |

**现象**：老师端删除学生报 500。

**根因**：`partner_claims` 与 `submissions` 两表引用 `students(id)` 时**漏写 `ON DELETE CASCADE`**，删除学生被外键阻塞。这两个表的 `init.sql` 里已经写对了，但**生产库是先建表后补的**，历史表结构的约束没跟上。

```sql
ALTER TABLE partner_claims DROP CONSTRAINT IF EXISTS partner_claims_student_id_fkey;
ALTER TABLE partner_claims ADD CONSTRAINT partner_claims_student_id_fkey
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE;
-- submissions 同理
```

**验证**：线上删除学生返回 204，关联数据一并清除。

**预防**：
1. **外键必须显式声明删除策略**（`CASCADE` / `SET NULL`），不允许默认 `NO ACTION`；
2. 迁移脚本编写时必须同时更新 `init.sql`，保证「新装环境」与「升级后环境」表结构一致；
3. 删除类操作必须纳入验收清单（3.7 / 2.7）。

## INC-005 登录返回 Internal Server Error

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | `91feb29` |
| 严重度 | 高（完全无法使用） |

**现象**：老师登录界面显示 `Internal Server Error`（纯文本，非 JSON）。日志中 `POST /api/auth/login` 返回 **200**，但紧随其后的接口出现异常。

**排查过程（关键：先读日志，不盲改）**：

```bash
docker logs --tail 80 gp-api
```

日志显示登录本身 **200 正常**，但 `/api/classes` 之后的链路异常；进一步用 curl 直连验证：

```bash
# 登录 OK，拿到 token
curl -sS -X POST https://gp.mealpick.me/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"luyulin@mealpick.me","password":"yourPassword123"}'   # → 200 + token

# 但带 token 访问受保护接口 → 401「未登录或登录已失效」
curl -sS -i https://gp.mealpick.me/api/classes -H "Authorization: Bearer $TOKEN"
```

**根因**：`server/src/index.js` 的鉴权钩子：

```js
app.decorate('authenticate', async (req, reply) => {
  try {
    await req.jwtVerify();
  } catch (err) {
    reply.code(401).send({ error: '未登录或登录已失效' });   // ← 缺少 return！
  }
});
```

Fastify 中钩子调用 `reply.send()` 后**不会自动中断后续处理**：钩子返回后，路由处理器仍会执行，此时 `req.user` 为 `undefined`，访问 `req.user.sub` 抛 `TypeError`，被 `setErrorHandler` 兜成 **500 纯文本**——与截图表现完全一致。

**修复**：

```js
  } catch (err) {
    // 必须 return，否则钩子放行后处理器仍会执行、取 req.user 抛错变成 500
    return reply.code(401).send({ error: '未登录或登录已失效' });
  }
```

同时加固前端：`GP.login()` 中的 `pullAll()` 包 try/catch，避免「登录成功但同步失败」被误报为登录失败。

**验证**：
- 错误密码 → **401**（不再是 500）；
- 正确密码 → 200 + token，受保护接口 200。

**预防**：
1. **Fastify 钩子中任何 `reply.send()` 必须 `return`**（已写入 [`../05-研发流程与规范/代码与提交规范.md §2.2`](../05-研发流程与规范/代码与提交规范.md)）；
2. 登录链路必须测「错误凭据」路径，验收清单 0.3 / 1.4 已固化；
3. 排查顺序固定为：**读日志 → 定位文件行 → 一次改好 → 复验**；本次排障过程中出现过一个反面操作：在 shell 里用 `sed 's/.*"token":"$[^"]*$".*/\1/'` 抓 JSON，因转义问题报 `invalid reference \1` —— 正确做法是用 `node -e` / `python -c` 解析 JSON（已记入 [`../04-技术设计/API接口文档.md §3.1`](../04-技术设计/API接口文档.md)）。

## INC-006 批量导入学生提示失败（`act_points` 聚合错误）

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | 4fd168d |
| 严重度 | 高（老师无法维护花名册） |

**现象**：老师端「花名册」导入 3 个名字（孙少奇 / 陈定涛 / 张卫良）后，界面提示「**导入失败：Internal Server Error**」，且顶部 toast 显示「添加未同步，数据仍在本机」。

**排查过程**：

```bash
docker logs --tail 80 gp-api
```

日志关键片段：

```
req-8  POST /api/classes/d9e1b6d8-.../students   → 201   ← 新增其实成功了！
req-9  GET  /api/classes/d9e1b6d8-.../state      → 500
       DatabaseError: column "a.act_points" must appear in the GROUP BY clause
                      or be used in an aggregate function
       at .../src/routes/events.js:153
       code: 42803
```

**根因**：`server/src/routes/events.js` 的「光荣榜」查询（`boardRows`）：

```sql
SELECT s.id, s.name,
       (COALESCE(SUM(e.delta), 0) + COALESCE(a.act_points, 0))::INT AS growth,   -- ← 问题在这
       ...
  FROM students s
  LEFT JOIN events e ON e.student_id = s.id AND e.class_id = $1
  LEFT JOIN ( SELECT student_id, SUM(points)::INT AS act_points
                FROM student_activities WHERE class_id = $1 GROUP BY student_id ) a
         ON a.student_id = s.id
 WHERE s.class_id = $1
 GROUP BY s.id, s.name
```

该查询含 `GROUP BY s.id, s.name`，而 `a.act_points` 既不在 `GROUP BY` 中、也没有被聚合函数包裹 → Postgres 报 `42803`。

> 为什么第一段 `studentRows` 查询没报错？因为**它没有 `GROUP BY`**（`s` 与两个已聚合子查询做行连接），非聚合列可以直接取。第二段为了算 `SUM/COUNT` 必须 `GROUP BY`，规则就变了。这个差异是本次踩坑的关键。
>
> 另外：`a.act_points` 之所以存在，是因为 Phase 2 新增了「把学生自主活动积分并入成长值」的功能（提交 `04e4225`），改动时只验证了第一段查询（老师大屏首屏能打开），**没有验证第二段聚合查询**——而它恰好在每次导入学生后的自动刷新时被触发。

**为什么显示成「导入失败」**：学生其实已成功入库（201）。前端 `importBatch()` 把 `POST /students` 与 `refreshFromCloud()` 串在同一个 `.catch` 里，刷新失败被当成导入失败 → **错误提示误导了老师**（老师会以为数据没进去，从而重复导入）。

**修复**：
1. 后端：改为 `COALESCE(MAX(a.act_points), 0)::INT`（`a` 子查询按 `student_id` 分组后每人仅一行，`MAX` 等价取值，且满足聚合要求）：

```sql
(COALESCE(SUM(e.delta), 0) + COALESCE(MAX(a.act_points), 0))::INT AS growth,
```

2. 前端：把「新增」与「刷新」的成功判定拆开：

```js
GP.api('/api/classes/'+remoteClassId()+'/students',{method:'POST',body:JSON.stringify({names:fresh})})
  .then(()=>refreshFromCloud()
    .then(()=>{ /* 提示：已导入 N 位 */ })
    .catch(()=>{ /* 提示：已导入 N 位，但花名册刷新超时，请手动刷新页面 */ }))
  .catch(err=>{ /* 提示：导入失败 */ });
```

**验证**（2026-09-11 服务器已验证）：

```bash
CID=$(curl -sS https://gp.mealpick.me/api/classes -H "Authorization: Bearer $TOKEN" \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).classes[0].id))")
curl -sS -o /dev/null -w '%{http_code}\n' "https://gp.mealpick.me/api/classes/$CID/state" -H "Authorization: Bearer $TOKEN"
# 结果：200（此前为 500）✅ 导入后自动刷新不再报错，导入提示正常
```

**预防**（本期已固化）：
1. **SQL 规则**：凡含 `GROUP BY` 的查询，SELECT 中的每一个非聚合列都必须出现在 `GROUP BY` 里，或包在聚合函数内。已写入 [`../04-技术设计/数据库设计.md §4.1`](../04-技术设计/数据库设计.md#41-全班状态聚合eventsjs124) 与开发自检清单；
2. **改动聚合查询时必须整体验证**：`/state` 有两段聚合查询，改一段必须同时跑另一段；
3. **接口层最小集成测试（Phase 4 首要补测项）**：`/state` 的聚合查询正是历史两次踩坑点（外键、聚合），必须纳入自动化；
4. **前端错误提示必须准确划分阶段**：区分「请求失败」与「刷新失败」，禁止用一个 `.catch` 吞掉不同阶段的错误——错误提示不准确本身就是一个缺陷；
5. 部署后冒烟必须包含 `GET /api/classes/:id/state`（验收清单 0.6）。

## INC-007 删除学生报 Bad Request（400，空 JSON body）

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | ac055b2 |
| 严重度 | 中（老师无法删除认领错误的学生） |

**现象**：老师在花名册里删除「认领错误」的同学，界面报 `Bad Request`（截图）。

**排查**：截图显示 `Bad Request`（400，非 500）。用最小 Fastify 复现：对 `DELETE` 请求带 `Content-Type: application/json` 但无 body，Fastify 直接返回 `400 FST_ERR_CTP_EMPTY_JSON_BODY`；去掉 JSON 头或带上合法 body 则正常。

**根因**：前端 `GP.api()` 统一给所有请求设置 `Content-Type: application/json`，即使是「删除学生」这种没有 body 的 `DELETE`。Fastify 5 在声明了 JSON 类型却收到空 body 时会抛 400（空 body 解析错误），删除因此失败。

**修复**（双层，双保险）：
1. 前端：`GP.api()` 仅在 `opt.body` 存在时才设置 `Content-Type`，无 body 的 `DELETE` 不再带 JSON 头；
2. 后端：`server/src/index.js` 注册自定义 `application/json` content type parser，遇到空 / 未定义 body 直接解析为 `undefined`，不再抛 400；真正的非法 JSON 仍返回 400。

**验证**：
- 最小 Fastify 复现：OLD → 400；NEW → 204；
- 服务端加固用例：DELETE 无 body → 204、正常 POST → 200、非法 JSON → 400、无 content-type 无 body → 200，均符合预期；
- `npm run check` 10/10 通过。

**预防**：
1. 凡「声明 application/json 但可能无 body」的请求（典型：`DELETE`），前端不要无条件带 JSON 头；
2. 后端对 content type parser 做空 body 容错，避免框架默认行为坑到无 body 请求；
3. `fetch` 封装层对「是否带 body 才带 JSON 头」形成统一约定，写入开发自检清单。

## INC-008 入班链接自动恢复上次身份，跳进已认领同学

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | 待修复 |
| 严重度 | 中（学生打开链接进到别人的界面） |

**现象**：老师「复制入班链接」发给学生，学生打开后**没有出现「你是哪位同学」的选择页**，而是直接进入某个已认领同学（如「机械生态 · Lv1」）的「我的伙伴」主页。

**排查**：读 `frontend/partner-demo.html` 的入口逻辑：

```js
(function init(){
  const m=location.search.match(/[?&]code=([^&]+)/); if(m) $('codeInput').value=m[1].trim();
  let saved=null;
  try{ saved=JSON.parse(localStorage.getItem('gp_me')||'null'); }catch(e){}
  if(saved && saved.classCode && saved.studentId){
    restoreHome(saved.classCode, saved.studentId);   // ← 有本地记录就直接恢复
  }
})();
```

`restoreHome()` 拉取 `/api/join/{saved.classCode}`，只要该学生已认领，就 `loadHome()` 直接进主页，**完全跳过选自己**。

**根因**：学生端把「本机记住的身份」当成了「当前访问者」。在**共用设备**（教室电脑、机房、老师演示机）上，上一个认领过的同学会被自动恢复，对下一个学生而言就是「随机跳到了某个同学」。更严重的是，`restoreHome` 用的是**上次保存的班级码**而非 URL 里的班级码，理论上可跨班恢复。

**修复方向**（见 [`../03-产品设计/产品定位与角色权限设计.md §五`](../03-产品设计/产品定位与角色权限设计.md)）：
1. 入班链接只带班级码，**身份一律重选**；不再自动 `restoreHome`；
2. 认领成功后签发**设备令牌**（绑定 `student_id` + `class_id`），写活动凭令牌校验；
3. 令牌跨班失效，杜绝串班。

**验证（修复后应满足）**：新设备/清缓存打开链接 → 停在「选自己」；已认领学生选自己名字 → 进自己的主页；换设备打开 → 仍要求选自己。

**预防**：
1. 「本地缓存身份」永远不能等同于「当前操作者」，凡涉及写入的接口都要有身份令牌；
2. 共用设备场景必须作为**首要场景**设计（教室就是共用设备）；
3. 新增「身份/权限」类改动时，必须走设计基线 §三 的权限矩阵评审。

## INC-009 「重新认领」入口无效，无法更换伙伴

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | 待修复 |
| 严重度 | 中（承诺的「重新认领」实际改不了伙伴） |

**现象**：用户问「怎么实现的重新认领」。点学生端页尾「切换账号 / 重新认领」后，回到输码页；重新输入班级码、点自己名字，却**直接回到原来的主页，无法重新选伙伴**。

**排查**：`resetAll()` 只清 `localStorage.gp_me` 并显示第一步；真正卡住的是 `pickStudent()`：

```js
function pickStudent(s, el){
  ...
  if(s.partner_kind){      // 已认领过 → 直接进主页
    loadHome();
    return;                // ← 不会再走到 renderLib()（选伙伴）
  }
  renderLib();
  ...
}
```

**根因**：流程只有「首次认领」一条路径。一旦 `partner_kind` 存在，就永远走「回主页」分支，「重新认领」既没有入口、也没有绕过分支的条件，属于**设计遗漏**（不是纯 bug）。

**修复方向**：
1. 增加明确的「🎨 更换伙伴」按钮 → 进入 `stepPick`（可预选当前伙伴）；
2. `pickStudent` 增加 `forceRepick` 参数，跳过「已认领 → 直接回主页」分支；
3. 更换时写一条新的 `partner_claims` 记录（保留变更历史）；是否限次见设计基线 Q5。

**预防**：
1. 任何「重置 / 重新 X」按钮，交付前必须**实测一遍完整走通**，不能只验证按钮有反应；
2. 「首次」与「重复」两条路径要一起设计，不能只做首跑；
3. 状态机类流程（未选→已选→已认领）要在设计文档里画出所有分支。

## INC-010 课间答题由学生自证对错，分值失真

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-11 |
| 提交 | 待修复 |
| 严重度 | 中（分值不可信、与「学生不能随意加分」定位冲突） |

**现象**：学生点「课间答题」，弹出 `confirm('你答对这道题了吗？ 确定=答对(+2)，取消=答错')`——**没有题目**，学生自己点「确定」就 +2。

**排查**：`frontend/partner-demo.html` 的 `doActivity`：

```js
if(kind==='quiz'){
  const ok=confirm('你答对这道题了吗？\n确定=答对(生态值+2)，取消=答错(不加分)');
  body.correct=ok;      // 对错由学生自报
}
```

服务端 `POST /api/students/:id/activity` 只按 `body.correct` 定分（`points = correct ? 2 : 0`），**没有题目、没有答案比对**。

**根因**：这是**设计缺陷**，不是编码错误。答题本应「工具出题 → 学生选答 → 服务端判分」，实现时退化成「学生自证」。根子上是缺了「题目」这一实体（R33 题库未做），也没有「判分权必须在服务端」的约束。

**修复方向**（见 [`../03-产品设计/产品定位与角色权限设计.md §六`](../03-产品设计/产品定位与角色权限设计.md)）：
1. 新增 `questions` 表（年级/单元/题干/选项/答案/解析）；
2. `GET /api/quiz/next` 出题（**响应不含答案**）；
3. `POST /api/students/:id/quiz { question_id, choice }` 由**服务端比对判分**；
4. 前端删除 `confirm` 自证弹窗；错误答案展示解析、不加分。

**预防**：
1. **判分权、计分权一律在服务端**——前端只提交「原始动作」，不提交「结论」；
2. 凡是「学生可得分的互动」，都必须有服务端可验证的「客观依据」（题答对 / 老师确认 / 每日唯一）；
3. 新增学生可得分项时，先在设计基线 §六 的规则表里登记「加分条件」，否则不予实现。

## INC-011 点击「认领我的伙伴」返回 Bad Request（400，partner_kind 非法）

**时间**：2026-09-13
**影响**：学生自选页选伙伴后点「认领」线上阻断，无法完成伙伴认领。
**现象**：`POST /api/students/:id/partner` 返回 400 `Bad Request`，后端日志 `partner_kind 非法`。

**根因**：**前后端 kind 清单不同步**。前端 `partner-demo.html` 的 LIB 数组在 R76 形象重做中新增了 5 个 kind（`brachio`/`stego`/`raptor`/`comet_tail`/`pulsar_star`），但后端 `server/src/routes/students.js` 的 `PARTNER_KINDS` 数组未同步追加。学生选了新 kind 提交认领时，后端 `PARTNER_KINDS.includes(partner_kind)` 校验不通过 → 400。

**修复**：
1. 后端 `PARTNER_KINDS` 追加 5 个新 kind（`brachio`/`stego`/`raptor`/`comet_tail`/`pulsar_star`）；
2. Python 校验脚本确认前后端 kind 完全一致（52:52，无差异）。

**证据**：`server/src/routes/students.js` `PARTNER_KINDS`、`frontend/partner-demo.html` LIB 数组、校验脚本输出 `be_set == fe_set`。

**预防**：
1. **凡在前端 LIB 新增 kind，必须同步后端 `PARTNER_KINDS`**——纳入构建体检清单（`build-frontend.sh` 可加前后端 kind 一致性校验）；
2. 前后端「枚举清单」类字段（kind / pack / rarity 等）改动后，用脚本做集合一致性校验，不靠人工记忆；
3. 学生认领是线上关键路径，新增 kind 后必须实际走一遍「选→认领→进主页」全流程，不能只看接口状态码。

**关联需求**：R75（修复 Bad Request）、R76（形象重做导致新增 kind）。

## 附录：跨事故的共性根因总结

| 共性根因 | 涉及事故 | 系统性对策 |
|---|---|---|
| **改动一处，未验证关联路径** | INC-004、INC-006、INC-011 | 改动聚合/外键类逻辑必须跑全链路；纳入冒烟清单 |
| **错误提示不准确，误导使用者** | INC-006、INC-002 | 提示必须区分失败阶段；不允许一个 catch 兜所有 |
| **第三方依赖阻塞关键路径** | INC-003 | 第三方脚本一律延迟加载 |
| **框架特性理解不到位** | INC-005（钩子需 return）、INC-001（HTML 解析） | 踩坑后立刻写入规范文档，形成团队记忆 |
| **构建/替换逻辑过于宽泛** | INC-002 | 精确匹配替换，构建脚本加注释警示 |
| **部署后只看接口状态码** | INC-001、INC-011 | 部署验收必须「打开页面 + 点通关键路径」（含认领全流程） |
| **缺身份/权限模型，前端自证结论** | INC-008、INC-009、INC-010 | 建立[角色权限基线](../03-产品设计/产品定位与角色权限设计.md)；判分权与身份校验一律在服务端；「重置/重新」类按钮必须实测走通全流程 |
| **前后端枚举清单不同步** | INC-011 | 前端 LIB 新增 kind 必须同步后端 `PARTNER_KINDS`；构建脚本加集合一致性校验 |
