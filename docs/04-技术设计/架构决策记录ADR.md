# 架构决策记录（ADR）

> 格式参考业界通行的 ADR（Architecture Decision Record）：**背景 → 决策 → 理由 → 代价 → 状态**。
> 只记录「会长期影响项目形态」的决策，普通实现细节不在此列。

---

## ADR-001 前端采用无框架的单文件 HTML

- **状态**：✅ 采纳（Phase 0 至今）
- **背景**：使用者是小学老师，课堂环境是教室电脑 + 投影；可能出现校园网慢、机器上没装 Node、临时换教室等情况。老师不会为了打开一个工具去装环境。
- **决策**：老师端与学生端都为**自包含的单文件 HTML**（内联 CSS/JS，无 CDN、无构建、无 npm 依赖）。双击即可运行。
- **理由**：
  1. 「换台电脑双击就能用」是不可替代的课堂体验；
  2. 弱网环境下不受 CDN 影响，首屏只有一次 HTML 请求；
  3. 部署极简：`git pull` + 拷贝文件即可，前端不需要构建机；
  4. 避免了「框架版本升级」带来的长期维护成本。
- **代价**：
  - 单文件 1400+ 行，可读性下降（用注释分区缓解）；
  - 无组件复用，老师端与学生端的 `creature()` 需各自维护（用「一致性 SOP」约束，见 [`../03-产品设计/伙伴图鉴设计（38种）.md §4`](../03-产品设计/伙伴图鉴设计（38种）.md)）；
  - 无法使用 TypeScript / 单元测试工具链。
- **替代方案与放弃原因**：
  - React/Vue + Vite：开发体验更好，但引入了构建与部署依赖，违背「零安装」；
  - 微信小程序：需要老师装微信开发者工具、学生需家长授权，门槛更高。

## ADR-002 使用独立子域名 + 宿主 Nginx 反代，而非子路径

- **状态**：✅ 采纳（Phase 1）
- **背景**：服务器 80/443 已被 MealPick 主站与 Umami 占用。最初尝试用 `gp-web` 容器托管前端，与宿主 Nginx 抢 80 端口失败（提交 `67e5c9d` 回退）。
- **决策**：使用**独立子域名** `gp.mealpick.me`；前端静态文件由**宿主 Nginx** 托管；`location ^~ /api/` 反代到 `127.0.0.1:3100`；不再启动前端容器。
- **理由**：
  1. 前端 JS 请求的 API 路径是 `/api/...`（根路径），若挂在 `/gp/` 子路径下会与主站后端 `/api/` 冲突；
  2. 独立子域名下 Cookie/同源策略最简单，免 CORS；
  3. 复用宿主 Nginx 与既有 certbot 证书体系，不额外维护容器化网关。
- **代价**：必须在 DNS 加 A 记录；每个新站点需一份 Nginx 配置与证书。
- **备注**：`gp-api` 与 `gp-db` 端口只绑 `127.0.0.1`，不对公网暴露。

## ADR-003 独立 `gp-db` 实例，不复用 umami-db

- **状态**：✅ 采纳（Phase 0，提交 `9836ea6`）
- **背景**：同机已有 `umami-db`（5433）与 MealPick 的数据库。
- **决策**：新增**独立的 `gp-db`** 容器（postgres:14-alpine，端口 5434，库 `growth_planet`）。
- **理由**：
  1. **故障隔离**：学生数据与主流业务数据互不影响，一次误操作不会连带事故；
  2. **权限最小化**：`gp_app` 用户只能访问 `growth_planet`；
  3. **可独立备份/迁移/销毁**：试用期结束后可单独清理。
- **代价**：多一个容器与一份数据卷；内存占用增加（试用期可接受）。

## ADR-004 后端使用 Fastify + 裸 SQL，不引入 ORM

- **状态**：✅ 采纳
- **背景**：后端只有 4 个路由文件、7 张表、约 500 行业务代码。
- **决策**：Fastify 5 + `pg` 直接写参数化 SQL，不引入 Prisma/TypeORM/Sequelize。
- **理由**：
  1. 查询全部可读、可 `EXPLAIN` 调优（如 `/state` 的多段聚合）；
  2. 无 schema 生成步骤，改表只需跑幂等迁移脚本；
  3. 依赖极少（4 个生产依赖），构建快、攻击面小。
- **代价**：
  - 聚合查询容易出错（**已实际踩坑**：`a.act_points` 未聚合导致 42803，见 [`../06-测试与验收/故障复盘记录.md`](../06-测试与验收/故障复盘记录.md#inc-003)）；
  - 无类型安全的查询构造，字段改名需手工全局搜索。
- **缓解**：在 [`../04-技术设计/数据库设计.md §4.1`](数据库设计.md#41-全班状态聚合eventsjs124) 固化「带 GROUP BY 的查询必须聚合」规则。

## ADR-005 学生端免登录，凭 `student_id` 写入

- **状态**：✅ 采纳（Phase 1.5）
- **背景**：小学生记不住账号密码；课堂时间宝贵；若强制登录会显著降低认领率（目标 ≥ 80%）。
- **决策**：学生端不设账号。`/api/join/:code`、`/api/students/:id/claim`、`/api/students/:id/activity(s)` 四个接口**显式不挂鉴权钩子**。
- **风险控制**：
  1. 只开放**无害动作**（认领、签到、答题、观察），不能点评他人、不能改分数；
  2. 分值由服务端按 `kind` 决定，客户端传 `correct` 最多只影响 2 分；
  3. 签到按天去重；
  4. `student_id` 是 UUID，不可枚举；
  5. 认领可被老师端覆盖（`PUT /api/students/:id`）。
- **代价**：理论上知道 `student_id` 的人可以代签到。试用期接受（RK-02）。
- **后续**：若推广到多校，需补「学生端一次性令牌」（老师生成入班链接时签发短时 token）。

## ADR-006 分值不由客户端传递，全部服务端定分

- **状态**：✅ 采纳
- **背景**：前端可被篡改；课堂上「刷分」会直接摧毁工具的公平性。
- **决策**：`POST /api/events` **不接受 `delta`**，只接受 `label_key`；`POST /api/students/:id/activity` 只接受 `kind`，分值由服务端常量表决定。
- **理由**：单点可信；前端可随意重构而不影响计分正确性。
- **代价**：调整分值必须改服务端并重新发布（`labels.js`）。
- **衍生决策**：`events` 表存 `delta` **快照**，保证历史记录可审计，不随标签调整而回溯变化。

## ADR-007 负向行为设计为「可恢复」，而非扣分排名

- **状态**：✅ 采纳（Phase 1）
- **背景**：面向小学生，公开扣分 / 排名靠后容易造成羞辱与对抗，家长也可能有意见。
- **决策**：
  1. 负向标签独立分组「恢复组」，`eco: 0`（不拖累班级生态值）；
  2. 负向只作用于伙伴状态（`droop` / `hurt`），并可视化「蔫了」；
  3. 提供 **`care: true`** 照料动作与正向点评两条恢复路径；
  4. 负向数据不进任何光荣榜。
- **理由**：把「行为纠正」转化为「照顾伙伴」的正向叙事，符合小学阶段教育理念。
- **代价**：老师看不到「负面清单」，难以做行为追踪（若后续有需求，可加老师可见的私有记录）。

## ADR-008 取消「按年级限制图鉴类型」，改为推荐 + 自由选择

- **状态**：✅ 采纳（Phase 2，提交 `6e28c34`）
- **背景**：原设计按 1–2/3–4/5–6 年级限定可选伙伴包，用户明确反馈「不要限制每个年级只能选择某一个类型的图鉴伙伴」。
- **决策**：学生端顶部加「全部 / 萌系自然 / 生命观察 / 动漫原创」标签，**任意年级可选任意伙伴**；年级只决定**默认高亮**哪个包。
- **理由**：
  1. 学生的收集动机是产品核心动力，限制会削弱它；
  2. 五年级孩子喜欢可爱小动物是正常的，不该被规则拒绝；
  3. `theme_pack` 仍保留在建班逻辑里，作为「推荐」而非「约束」。
- **代价**：失去「按学段引导学习内容」的教育设计感 → 后续通过**默认高亮**与**内容关联（题库按年级）**补偿。

## ADR-009 前端保留「云同步层」的本地降级能力

- **状态**：✅ 采纳
- **背景**：教室网络可能不稳定；后端可能重启；老师不能因为「后端挂了」而无法上课。
- **决策**：老师端数据**始终先写 localStorage**，云端同步是增强；`GP_API_BASE` 未注入或请求失败时自动退回本地模式，并明确提示「未同步，数据仍在本机」。
- **理由**：课堂工具的可用性优先于数据实时一致性。
- **代价**：存在「本地与云端不一致」的窗口；需靠 `refreshFromCloud()` 与明确提示收敛。

## ADR-010 版本策略：按 Phase 交付 + 语义化 tag

- **状态**：✅ 采纳（Phase 2.1 起）
- **决策**：每次线上部署对应一个语义化版本（`v0.1.0` / `v0.2.0` / `v0.2.1`…），tag 打在部署所用的提交上；`CHANGELOG.md` 与 tag 一一对应。
- **理由**：试用期需要「能随时回滚到上一个能用的版本」；单人开发更需要低成本的可追溯性。
- **代价**：每次发布多两步（打 tag、写 changelog）——用 `05-研发流程与规范` 的发布清单约束。
